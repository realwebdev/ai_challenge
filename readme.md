# Go & Ollama Code Review Streamer

A modular, production-ready Go backend that interfaces with a local Ollama server using its OpenAI-compatible endpoint. This repository demonstrates the progression from basic synchronous HTTP interactions to multi-turn structured Server-Sent Events (SSE) featuring resource lifecycle safety and token metric extraction.

---

## 📁 Repository Structure

The project is divided into three distinct command files inside the `cmd/` directory, each showcasing a specific step in evolutionary development:

```text
├── cmd/
│   ├── 1-simple/         # Simple blocking request-response
│   ├── 2-stream/         # Real-time token streaming with lifecycle controls
│   └── 3-chat-metrics/   # Multi-turn conversational chat with usage extraction
├── README.md             # Project documentation
└── go.mod
```

---

## ⚙️ Architecture & Component Breakdown

### 🎯 1. Simple Request-Response (`cmd/1-simple/`)
* **Purpose**: Demonstrates the baseline configuration for blocking, unary operations.
* **Mechanics**: Implements standard `application/json` request encoding and decoding. It waits for the upstream LLM to finish generation entirely before releasing the network thread. 
* **Target Scenario**: Quick prototyping, automated backend tests, and non-time-critical scripting tasks.

### ⚡ 2. Streaming Response (`cmd/2-stream/`)
* **Purpose**: Implements real-time text delivery leveraging **Server-Sent Events (SSE)** protocol semantics (`text/event-stream`).
* **Key Mechanisms**:
  * **Dynamic Buffer Flushing**: Employs Go's native `http.Flusher` interface to bypass server-side network buffering. Tokens are pushed to the client immediately as they are generated by the model.
  * **Client Disconnection Detection**: Monitors the incoming `r.Context().Done()` block via a non-blocking `select` loop inside the scanner. If a browser tab closes or a terminal `Ctrl+C` interrupt occurs, the handler exits immediately.
  * **GPU Resource Preservation**: Because the upstream client is built via `http.NewRequestWithContext(r.Context(), ...)`, dropping the user-facing network socket automatically cancels the upstream request to Ollama, instantly liberating local GPU/VRAM resources.

### 📊 3. Conversational Session & Metrics (`cmd/3-chat-metrics/`)
* **Purpose**: Provides a foundation for chat applications capable of tracking continuous state and system overhead.
* **Key Mechanisms**:
  * **State Retention (Multi-Turn Chat)**: Shifts from single stateless prompts to parsing a structured session history payload (`[]Message`). By forwarding the conversation array on each request, it allows the model to retain contextual memory.
  * **Structured Usage Extraction**: Parses the trailing meta-chunk issued by Ollama just before the `[DONE]` boundary. This extracts exact `prompt_tokens`, `completion_tokens`, and `total_tokens` variables to inject them natively back into the SSE stream as structured log artifacts.

## 🚀 Getting Started & Configuration

### 1. Enable Parallel Processing in Ollama
By default, Ollama queues inbound requests sequentially. To test true parallel execution across multiple client terminals or browser tabs when using the streaming variants, configure your system's VRAM scheduler before starting your Ollama server instance:

```bash
# macOS / Linux terminal
export OLLAMA_NUM_PARALLEL=4
ollama serve

# Windows PowerShell
\$env:OLLAMA_NUM_PARALLEL="4"
ollama serve
```

### 2. Run a Backend Target
Navigate to any of the command directories and fire up the Go web server (default port `:8084`):
```bash
go run cmd/3-chat-metrics/main.go
```

### 3. Test with Curl
Execute a multi-turn simulation by sending a conversation history payload down the streaming wire:

```bash
curl -N -X POST http://localhost:8084/review \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [
      {"role": "user", "content": "Write a quick Go add function."},
      {"role": "assistant", "content": "func add(a, b int) int { return a + b }"},
      {"role": "user", "content": "Can you change it to accept floats?"}
    ]
  }'
```

## 💡 Key Design Patterns Used

* **Resource Leak Protection**: Avoids background goroutine grouping inside continuous scanner loops to prevent unbounded scheduling growth.
* **OpenAI API Compatibility**: Maps cleanly to any production model gateway provider (Ollama, OpenAI, DeepSeek, Claude) using native Go structures.
* **Universal SSE Delivery**: Formatted text-line delivery compatible both with native web-browser `EventSource` wrappers and strict CLI network decoders.
